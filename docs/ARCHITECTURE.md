# tsukota-web アーキテクチャ

> このドキュメントは、tsukota-web の**技術選定**と**設計方針**を定義します。
> 「どう作るか」（アーキテクチャパターン、技術スタック、セキュリティ設計）を記載しています。
>
> 機能要件やAPI仕様など「何を作るか」については [SPEC.md](./SPEC.md) を参照してください。

## 概要

tsukota-web は [tsukota](https://github.com/bouzuya/tsukota) の Web 版であり、その設計思想を踏襲しています。

## 技術スタック

### フロントエンド

| レイヤー | 技術 | 説明 |
|---------|------|------|
| フレームワーク | React + Vite | SPA (Single Page Application) |
| 状態管理 | jotai | Atomic state management |
| スタイリング | Tailwind CSS | Utility-first CSS framework |

### バックエンド

| レイヤー | 技術 | 説明 |
|---------|------|------|
| サーバー | Rust + axum | 非同期 Web フレームワーク |
| データベース | Firestore | NoSQL ドキュメントデータベース |
| 認証 | Google OAuth + JWT | JWT 有効期限: 15分、リフレッシュトークン使用 |

### デプロイ

- **本番環境**: Cloud Run
- **開発環境**: Docker (ローカル)

### バックエンドのレイヤー構成

バックエンドは責務ごとに 4 つのレイヤーに分割された crate で構成されます：

| Crate | レイヤー | 責務 |
|-------|---------|------|
| `domain` | ドメイン層 | ビジネスロジック、集約、イベント定義。外部依存なし |
| `application` | アプリケーション層 | ユースケース、コマンド/クエリハンドラー。ドメインとインフラの調整 |
| `infra` | インフラ層 | データベースアクセス、イベントストア実装、外部サービス連携 |
| `api` | プレゼンテーション層 | REST API (axum)、リクエスト/レスポンス変換、認証ミドルウェア |

**依存関係の方向**：
```
api → application → domain
        ↓
      infra → domain
```

- 上位レイヤーは下位レイヤーに依存
- `domain` は他のどのレイヤーにも依存しない（依存性逆転の原則）
- `infra` は `domain` の trait を実装

## アーキテクチャパターン

### イベントソーシング

tsukota-web はドメインモデルの永続化に**イベントソーシング**を採用しています。

#### 集約 (Aggregate) の設計

- **集約の単位**: **アカウント**のみ
- **イベントストリーム**: 各アカウントが独立したイベントストリームを持つ
- **集約の境界**: 分類 (Category) と取引 (Transaction) はすべてアカウントの一部として扱う

この設計により、以下の利点があります：

- アカウント単位でのトランザクション整合性
- アカウント単位での並行処理の制御
- 監査ログとしてのイベント履歴

#### イベント定義

アカウント集約のイベント一覧は以下を参照：
https://github.com/bouzuya/tsukota/blob/master/packages/account-events/src/account-events.ts

#### ユーザーの扱い

**ユーザー (User) についてはイベントソーシングを使用していません**。

理由：
- ユーザーはアカウントとは独立した概念
- ユーザーのライフサイクルは認証プロバイダー (Google OAuth) に依存
- イベント履歴の管理が必要なビジネスロジックを持たない

### データモデル

#### イベントストア vs 読み取りモデル

- **イベントストア**: Firestore にアカウントごとのイベントを格納
- **読み取りモデル (Projection)**: イベントから構築されるビューモデル
  - `Account`: アカウント情報
  - `Category`: カテゴリ情報
  - `Transaction`: 取引情報

SPEC.md に記載されているデータモデルは、この読み取りモデルに相当します。

#### スキーマ定義

スキーマ定義は以下を参照：
https://github.com/bouzuya/tsukota/blob/master/packages/schema/src/schema.ts

### コマンド・クエリ分離 (CQRS)

イベントソーシングの採用により、自然に CQRS パターンが適用されます：

- **コマンド (Command)**: アカウント集約に対する操作 → イベント発行
- **クエリ (Query)**: 読み取りモデルからのデータ取得

これにより、書き込みと読み取りで異なる最適化が可能になります。

## セキュリティ

### 認証・認可

- **認証**: Google OAuth 2.0
- **トークン管理**:
  - アクセストークン: JWT (有効期限 15分)
  - リフレッシュトークン: 長期有効、HTTPOnly Cookie で管理
- **認可**: アカウント単位の権限管理
  - オーナー: アカウント削除、メンバー管理
  - メンバー: 収支・カテゴリの CRUD

### API セキュリティ

- **HTTPS 必須**: すべての API 通信を暗号化
- **CORS 設定**: 許可されたオリジンのみアクセス可能
- **入力検証**: すべての API リクエストで検証実施
