## Design Decisions

### 1. Generic Repository Pattern

Use cases are generic over repository/projection traits, enabling:
- Easy testing with mock implementations
- Dependency injection from API layer
- Clean separation from infrastructure details

### 2. View Models vs Domain Models

View models use `String` for IDs and dates instead of domain value objects:
- Matches API contract in SPEC.md
- Simplifies serialization
- Clear boundary between layers

### 3. Authorization in Application Layer

Permission checks happen in use cases, not domain:
- Domain focuses on business rules
- Application orchestrates authorization + domain logic
- Reusable across different use cases

### 4. Cursor-Based Pagination

Transaction listing uses cursor (last transaction ID):
- Efficient for large datasets
- Consistent with SPEC.md requirement
- Better than offset-based for distributed systems

### 5. Month-Based Export

Export functionality loads all transactions for a given month:
- Matches SPEC.md API: `/accounts/:id/export/json?year=YYYY&month=MM`
- Uses projection to filter by date range
- Returns full transaction details in JSON
