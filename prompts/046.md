# 046

- 新しい方針について検討します
- 更新作業として実行するのではなく、以下の項目について検討し、懸念点など意見を出してください

> - すべての use case について URL パス・リクエストボディでパラメーターを分割するのをやめます
> - SPEC.md を見直し、 RESTful API の採用を避けます
>     - 更新系の操作については `POST /commands/{use_case_name}` (use_case_name は snake_case) で受け取ります
>     - 参照系の操作についてはリソースの階層構造を維持します
>       - 例: `GET /accounts/{account_id}`
>       - 例: `GET /accounts/{account_id}/categories`

- パスパラメーターが `*Request` から漏れている点は入力がバラける点で問題
    - 対象 (パス) と操作内容 (ボディ) で分けた場合、対象が複数になるような操作で曖昧さが生まれる
    - 単純に操作とその内容（対象を含む）としたい
- 更新系ユースケースについては、この問題の回避のため `POST /commands/*` に集約する
- 参照系ユースケースについては、HTTP GET はリクエストボディを取らないため、入力がバラける問題は起きない
    - 今回は SPA ではあるものの、なるべく MPA でも動くクラシックな Web アプリケーションとして動作するパス設計にしておきたい
    - 参照時はリソースベースのパス構成を許容する
- 別案
    - リソースベースのパス構成を維持しつつ、更新系ユースケースについては入力 `Request` を詰め替える

別案と比較してどうかの意見をください。
